## Part A — Member-app simplicity and design

**A1 Baseline.** Capture desktop and 390px screenshots of the current member surfaces before any edit, so before/after hierarchy can be shown.

**A2 Navigation.** One hierarchy across desktop and mobile with five primary destinations: Today, Meals, Progress, Ask/Help, More. Each maps to the existing route (no duplicates). More is grouped as: Learn and tools (Learn, Library, Workouts where active); Community; Account and help (Profile, Billing, Settings, Support). Billing, Settings, Support, export and deletion stay reachable during billing restriction; Settings stays reachable during deletion restriction, driven by the existing account-surface evaluator and route precedence (`src/lib/appSurfaces.ts`, `src/lib/membership.ts`) — no component re-derives status. Fasting scheduling and Supplements do not return to primary navigation, onboarding, Today or the first-14-day journey; the education-only fasting guide stays reachable through Learn only. Disabled or empty tools are not surfaced to fill space. Every destination gets an accurate accessible label and active state.

**A3 Today dashboard.** Reorder to: calm greeting and short orientation → one visually dominant Today's Action card → a small row of existing logging shortcuts (blood glucose, meals, activity/habit — no new data fields) → one compact progress summary → secondary content. Only one primary call to action above the fold. Today's Action stays usable when catch-up exists. Streak, ring, level, XP and phase summaries are combined into a single progress element; detailed levels, badges and streak history move to Profile or a collapsed section; habit rings remain as supporting detail only. Upcoming days and journey previews sit below the current action or inside a collapsed journey section. Catch-up is collapsed by default with a neutral count and optional disclosure — no shame, urgency or failure language. Wording is "Daily Action Streak", never "Reversal Streak". No member data, achievement history, completed-state functionality or database fields are removed.

**A4 First use and Days 1–3.** Onboarding keeps only the fields the working membership needs (no fasting, supplement, medication-clearance or extra health questions), shows current step and what remains, and lands directly on Today's Action. Days 1–3 each present one main action plus supporting explanation and optional logging. Inline guidance uses existing UI patterns rather than a new tutorial system. Empty states explain the next step; error states offer recovery and preserve entered input where safe; loading states never look like empty data or failure.

**A5 Core screens.** Meals: ideas and plans easy to find, next useful action obvious, AI-generated labels/safety notes/reporting preserved, advanced generation and export behind a secondary action, no supplement or fasting plan modes. Progress: one clear summary before detailed charts, doctor report stays inside Progress, charts get text summaries, non-color-dependent legends and accessible table equivalents where practical, S1 classifications preserved, no new urgent-high rule. Ask/Help: public VITA widget stays the Stage 0 deterministic membership helper; the signed-in Ask screen describes only what is enabled today and — with health AI disabled — makes no personalized-health promise, keeps emergency/medication boundaries, AI-generated/educational labels and reporting, and keeps safe paths to support and community questions; no invented credentials or "expert-reviewed" wording. Community: honest empty state, no fabricated activity or members, stays under More, moderation and privacy controls intact. Account screens: consistent headings, actions and status language across Billing, Profile, Settings and Support; signed-in members are never sent to Login because of billing status; billing-restricted, dispute-restricted and deletion-restricted states get calm explanations and clear recovery; export, deletion, cancellation and support stay findable.

**A6 Terminology.** Standardize on Today's Action, Daily Action Streak, Progress, Meals, Ask VITA or Help (matching the enabled capability), Build Your Routine, educational membership. Remove active member-facing remnants of Reversal Streak, "Phase 3 — Reversal", reverse/reversal as a promised benefit, 7-Day Reset and 7-Day Reset Sprint, guaranteed or typical medical outcomes, unsupported expert/rating/testimonial/member-count claims, and mandatory fasting or supplement language. The scan distinguishes prohibited positive claims from the approved negative disclaimer ("does not diagnose, treat or promise to reverse diabetes").

## Part B — Accessibility, mobile and performance

**B1 Accessibility.** Across public and signed-in core routes: one logical page-level heading, semantic landmarks, programmatic labels and descriptions, visible focus, logical focus order, dialog/sheet focus containment with Escape and focus return, errors tied to their fields, appropriately announced status and urgent messages, no color-only information, meaningful icon-button names, keyboard-operable tabs/menus/accordions/charts/actions, 44×44 CSS-pixel targets, sufficient contrast within the existing palette, reduced-motion respect, readable body text without zoom, usable at 200% zoom, no unexpected focus movement. Glucose warnings keep the approved live-region behavior; forced focus is added only if testing proves it necessary.

**B2 Mobile.** Verify 320px, 390×844, 768px and ≥1280px: no horizontal overflow; no clipped cards, tables, dialogs or charts; VITA, sticky actions, cookie/privacy controls and bottom navigation never collide; opening VITA hides or repositions conflicting fixed controls; the software keyboard never hides the active chat/input action; safe-area padding correct; long legal, email, URL and health-unit strings wrap; bottom navigation readable and reachable; Today exposes its primary action without excessive scrolling.

**B3 Performance.** No new large UI or chart dependency. Route lazy loading preserved. Record before/after production bundle size and largest chunks and investigate unexpected growth. Remove avoidable duplicate queries and repeated dashboard fetches. Keep the Billing race/unmount protections. Set dimensions on important images; no heavy autoplay media. Confirm no meaningful route-loading or interaction regression.

## Part C — Dependencies and lint

**C1.** Run the production-only and complete audits. For each high/critical advisory report package and advisory, direct vs transitive, runtime vs build/test-only, the actual import path, whether the vulnerable behavior is reachable in DRM, the smallest safe fixed version and the action taken or deferral reason. Prioritize React Router and other reachable browser/runtime risks if still present; reassess the Supabase transitive `ws` path rather than assuming it. Smallest compatible upgrade set, no blind forced fix, no unrelated upgrades, no unplanned major migration; move build-only tooling out of production dependencies where safe; lockfile updated normally. After each upgrade group run focused tests, typecheck and a browser smoke check. Build/test-only advisories may be deferred with reachability evidence; a reachable unresolved critical or high production vulnerability is reported as a release blocker.

**C2.** Repository-wide lint over active source and runtime files, excluding historical evidence/package copies that are not compiled or deployed. Fix all errors in touched files plus correctness, security, accessibility, Rules-of-Hooks and stale-effect findings across active source, grouping mechanical typing fixes. No behavior changes purely to silence lint. Target zero errors on active runtime source; list every remaining warning with rule, location and deferral reason; do not present duplicated historical findings as new debt.

## Part D — Security headers and source maps

**D1.** Inspect the actual hosting mechanism first and do not claim a meta tag provides header-only protection. Prepare the least-permissive compatible production policy for CSP, frame-ancestors (or equivalent anti-framing), Permissions Policy, COOP/CORP where compatible, existing HSTS, `X-Content-Type-Options: nosniff` and the existing referrer policy. Build the CSP from observed production connections: DRM origins, Supabase, Stripe, required font/image assets and currently approved APIs only — no `*`, no new analytics or reporting vendor, no silent weakening of exact-origin CORS. Test magic-link login, Stripe redirect/return, VITA, Supabase requests, downloads, printing and normal navigation; if COOP/CORP breaks an approved flow, use the safest compatible setting and document it. If hosting cannot apply a header before publication, prepare the supported configuration and list the exact post-publication verification.

**D2.** Disable production source-map output (no paid monitoring added), confirm the build output contains no deployable `.map`, and record the live `.map` URL check as post-publication verification.
